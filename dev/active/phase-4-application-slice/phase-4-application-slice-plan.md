# Phase 4: application slice and MCP addon (plan)

## Summary
ACTION-PLAN Phase 4: "Tauri/React: import, dashboard, breakdown viewer, item edit, async recalc, save JSON, export XML. Local MCP server with read-only default and approved writes." Gate: "end-to-end workflow on Windows and Linux; accessibility checks; MCP contract tests." ADR-013's first usable milestone lists the same workflow plus the MCP addon (ADR-017). IMPLEMENTATION-PLAN Phase 4 adds detail where it does not contradict the ACTION-PLAN, and the Phase 3 plan's decision 12 moved the application task, command history, background jobs, and autosave here.

**One PR (maintainer, 2026-11-13: "Complete phase 4 in the fewest number of PRs possible").** The plan, the implementation, and the gate report go in one PR, as the Phase 3 close-out did. The plan is reviewed by `plan-reviewer` in the same session before code is written; its findings are recorded in the context file.

## Current state (2026-11-13, `dev` at `24a331d`, PR #104 merged)
- Core: import (PoB XML, share code), resolution (`loom_parser::import::Resolver`), the engine (`loom_calc::calculate_cancellable`), the calc result document v1, the build document v1 with migrations, PoB XML and share-code export, all done and gated.
- Host: `loom-persistence` has `Store::load`/`Store::save` (atomic, never over the import's origin). `loom-app` and `loom-integrations` are empty. `loom-tauri` opens an empty window. `ui/` is a Vite scaffold with the generated build and calc result types.
- The pipeline from text to calc result exists only in `loom-parity-cli calc-run` (a tool; tools may not depend on host crates). It moves into a new core crate, `loom-pipeline` (decision 0), which both `calc-run` and `loom-app` call.

## Target state
A desktop app (Windows and Linux gated, macOS best effort) where a user: imports a PoB build (paste a share code or XML, or open an `.xml` file); reviews the import (lines read, matched, adapted, warnings); sees a dashboard of the calc slice's fields with their states; opens a field's breakdown (provenance graph, sources with stat IDs); edits an item's lines (replace, remove, add, numeric roll edits) with a preview of the effect, applied as one undoable step; sees recalculation run in the background; saves the build as build document v1; reopens it; exports PoB XML or a share code. A local MCP server, off until the user starts it, lets an MCP client read the build and its calculations, preview item edits, and request item edits that the user approves in the app (or under a standing grant they can revoke).

## Design constraints and decisions
0. **One pipeline (review finding 1).** The pure part of `calc_run::one` (read PoB XML, a share code, or a build document; resolve with range ends; item base names; PoB's line values; `CalcOptions`; calculate with a cancellation hook; the calc result document) moves into a new core crate `loom-pipeline` (depends on `loom-parser`, `loom-calc`, `loom-serialization`; wasm32 job, `clippy.toml`, `CORE_CRATES`, AGENTS.md updated). `calc-run` calls it, so the Phase 3 parity evidence covers the app's results; `calc-run`'s outputs on the public fixtures stay byte-identical (checked before and after).
1. **Data bundle.** The app calculates with one validated bundle folder: the user picks it in the app (stored in the app's config folder) or `LOOM_BUNDLE_DIR` names it. Signed shipped bundles are Phase 5. Without a bundle the app still opens and says what is missing; import needs one (resolution is part of import). The tree version comes from a table in `loom-app` keyed by game and the bundle's Steam build (`3_29` for 26530219), checked by a test against `docs/phase-3/calc-scope-poe1.json`; another Steam build calculates with no tree version (`Partial`, `unchecked-tree-version`), as `calc-run` does.
2. **Application layer (`loom-app`, ADR-004).** `Session` is the synchronous core: it owns the current state, an immutable `Arc<State>` of the `Build` with its range ends (review finding 3), its version, the undo and redo stacks, and the dirty flag; every command goes through `Session::execute`. `App` owns a `Session` on one thread (single writer) and takes commands from a channel; queries read the latest immutable snapshot (`Arc`). Events go to a sink the host gives (`Fn(Event)`), each with the snapshot version and the command's correlation ID.
3. **Commands.** `ImportText { text }` (share code or XML, detected), `EditItem`, `Undo`, `Redo`, `Save`, `OpenRecent { id }`, `Restore { id }`, `Discard { id }`, `Approve { id }`, `Decline { id }`, `Close`, `ExportShareCode` (returns the code): the API DTO's `Command`, none of which takes a path. The commands that take a path the user picked in a dialog (`ImportFile`, `Open`, `SaveAs`, `ExportPobXml`) are `loom-app` Rust types, never sent by the webview or an addon (review finding 11a). Recent builds and recovery snapshots are named by IDs the application issues (finding 11b). Import and open are atomic: on failure the session is unchanged. They reset history. Queries: the snapshot (build projection, calc document, versions, status), one item, the warnings, `PreviewItemEdit` (a what-if calculation, never committed).
4. **History.** Snapshot undo: each command that changes the build pushes the previous `Arc<State>` (build and range ends, so an undone edit calculates exactly as before it; a test checks byte equality) with a history entry (what, and whether the user or an MCP request made it, with the request's ID; findings 3, 14), limit 100; redo is cleared by a new change. Item edits, approved MCP edits, and their undo all take this path, so undo is consistent across panels and addon writes (ADR-009, ADR-017).
5. **Background recalculation (ADR-003).** After each change the app starts a calc job on a worker thread with the new snapshot. A newer change cancels the running job through `calculate_cancellable`'s hook; a result whose version is not the latest is discarded (stale). Events: `CalcStarted`, `CalcFinished`, `CalcFailed`, each with the version.
6. **Item edits.** An edit is a list of line operations on one item: `Replace { line, text }`, `Remove { line }`, `Add { text }` (a modifier line after the last explicit line). The app writes the item's text from its lines' sources with the edits applied, reads it with the PoB item reader (`pob_item::read`, `to_domain`), keeps the item's ID and untyped content, clears `text_spacing` (domain rule), and resolves it with the bundle. Lines that do not resolve stay as warnings (ADR-015). A numeric roll edit is a `Replace` whose text the UI builds from the line's numbers. The item's text is written by the same function the XML export uses (`pob_xml::item_text`, made public), so edit and export cannot disagree. A ranged line's roll is edited with `SetRange { line, value }`, which writes its `{range:r}` prefix and keeps the range (PoB's rolled values, P3-8b; finding 13). Every edit carries the snapshot version it was made against and each target line's expected text; a mismatch is refused with `APP_STALE_EDIT` (finding 4). The preview runs on a worker thread with a snapshot, never on the writer thread (finding 15), and returns each field of the calc document (not a fixed list; finding 16) with value and state before and after.
7. **Reopen recovers range ends; opening never needs data (finding 2).** A build document carries resolutions but not the exact ends of the ranges the resolver read, which the calc host needs for PoB's rolled values (P3-8b). Opening always succeeds and keeps the document's resolutions (ADR-009). When a bundle of the build's data version is loaded, the app resolves a clone with its lines reset to pending, only to recover the ends; if the clone's resolutions differ from the stored ones, the stored ones stay, the ends are not used, and the snapshot carries the warning `APP_RESOLUTION_CHANGED`. With no bundle, or another data version or game, the build is shown and the calculation reports its failure as a state with a stable code (`APP_NO_DATA`, `APP_DATA_VERSION`, `APP_GAME_MISMATCH`), never a crash or blank fields. Tests: import, save, reopen gives the same calc document byte for byte; reopen without data shows the build and the code.
8. **Persistence (ADR-009).** Save writes build document v1 through `Store::save` (atomic; never over the import's origin; replace only a build document). Export writes PoB XML to a new file the user picks. Autosave: after a change the host writes a recovery snapshot (a versioned file, `format: loom-recovery`, `version: 1`, holding a header (origin path, saved path, time) and the build document) to `<app data>/recovery/<instance>.json` at most every 2 s; each running instance holds an exclusive lock on `<instance>.lock` (`std::fs::File::try_lock`), and the start screen lists only snapshots whose lock is free, so a second instance never offers or deletes a live one (finding 12); a restore goes through the open path (decision 7); a save or a clean close deletes it; at start the app lists recovery snapshots and offers to restore or discard them. Recent builds: `<app data>/recent.json`, a rebuildable index (losing it loses no build). The SQLite index waits for search (IMPLEMENTATION-PLAN Phase 6 WP5); ADR-009's file-first rule holds without it.
9. **API DTOs and generated bindings (ADR-002).** The app API's projections, commands, and events are versioned DTOs in `loom_serialization::dto::app::v1` (a core crate, so `loom-schema-gen` may generate them). `schemas/app-api.v1.schema.json` is generated; `pnpm generate:schema` writes `ui/src/generated/app-api.v1.ts`; CI's schema job checks both are fresh. Errors carry their layer's stable code (ADR-014). The Tauri command names are a committed list (`ui/src/api/commands.json`) that the TS client reads and a Rust test compares with the registered handlers (finding 10).
10. **Tauri shell (ADR-002, IMPLEMENTATION-PLAN WP1).** `loom-tauri` is a thin adapter: commands call `loom-app`, events go to the webview as one `loom://event` channel. File access is user-mediated: the Rust side opens the file dialogs (`tauri-plugin-dialog`) and the webview never passes a path, except a recent build by its index in the recent list, which Rust checks. The capability file grants only the core defaults the window needs and the app's own commands; no `dialog:*` or `fs:*` permission reaches the webview, and a test reads the capability file to check it (finding 11c). The dialogs sit behind a `FilePicker` trait so tests drive the commands without a desktop.
11. **MCP server (ADR-017, ADR-010).** In `loom-integrations`: the MCP "Streamable HTTP" transport's request-response subset (POST of one JSON-RPC message, JSON response; no server-sent events; GET and DELETE get 405), on `127.0.0.1` only, an ephemeral port, a random bearer token (`getrandom`) made at each start and dead at stop, compared in constant time, the `Host` header required to be `127.0.0.1:<port>` or `localhost:<port>` and the `Origin` header refused unless absent or loopback (DNS rebinding), a 1 MiB body limit, one request at a time (so previews, each a full calculation, are serialized), at most 16 pending change requests. The HTTP layer is a small hand-written module on `std::net` (no new crate; finding 5g). No tool takes a file path, saves, or exports (ADR-010; finding 5f); the projections given to clients carry no file paths. Off until the user starts it in the app; the app shows the URL, the token, and a `claude mcp add` command. Protocol version `2025-06-18`. Tools, contract v1: `get_build`, `list_fields`, `get_breakdown`, `list_items`, `get_item`, `list_warnings`, `preview_item_edit` (read), `request_item_edit`, `get_request` (write requests). Permissions: read on while the server runs; change requests off by default (read-only default); when on, each request waits for Approve or Decline in the app, unless the user gives a standing grant, which applies requests at once and can be revoked; the grant is global, lasts until the server stops, and is never stored (finding 5e). A request carries the snapshot version it saw and the expected text of each line it targets, and is refused as stale when either changed (finding 4). Applied requests go through `EditItem`, so they are undoable and in history. The tool list is a committed contract file (`schemas/mcp-tools.v1.json`), compared by a test; tool results are app API v1 DTOs, named in each tool's description, so the two contracts version together (finding 18). The app makes no outbound connection and holds no key.
12. **UI (ADR-004, ADR-008).** React 19 + TypeScript + Vite. Redux Toolkit holds read projections (snapshot, calc status, proposals, MCP state); the import workflow is an explicit state machine (`idle → reading → review → done | failed`). React never changes canonical state: it sends commands and renders snapshots; a missed event version triggers a snapshot query. A `LoomApi` interface has a Tauri implementation and an in-memory fake for tests. Screens from `docs/ui/` in this slice: start (import, open, recent, recovery), import result, dashboard (offence, defence, warnings), breakdown, equipment list and item editor, warnings, AI connection with approvals, about (non-affiliation notice). Stages, dashboard customization, skills, passive tree, and configuration screens are later (out of scope). Colours from the brief's tokens; every status has a text label; copy in one message catalog (`ui/src/i18n/en.ts`); numbers through `Intl.NumberFormat`; reduced motion respected. Headless primitives: native elements where they suffice, Radix UI for the menu and dialog.
13. **Accessibility checks (ADR-008, WCAG 2.2 AA).** Vitest with jsdom and Testing Library: axe-core on every screen with no violations; keyboard tests (tab order, menu keys, Escape, focus moved to each screen's heading on navigation); a committed table of every foreground/background token pair (`ui/src/theme/pairs.ts`) tested for 4.5:1 (3:1 for the focus ring and non-text borders), and a test that the CSS writes colours only through the tokens (finding 9); error-state tests (no data, import failed, calculation failed, stale request) and an `aria-live` announcement of the calculation's status (finding 8). Zoom to 200 %, target size, and a screen-reader pass are in the real-app checklist (decision 14). CI runs them in the `frontend` job on Windows and Linux.
14. **End-to-end (gate).** Three layers, each on Windows and Linux in CI: (a) `loom-app` workflow test: import the synthetic PoE1 build with the synthetic bundle, calculate, edit an item, see the async recalculation with a new version, undo and redo, save, reopen (equal document and equal calc result), export XML and re-import it (semantically equal, `xml_equal` on the untouched build; the edited item's lines as edited), share code round trip; (b) `loom-tauri` IPC test: the same workflow through the real Tauri commands on Tauri's mock runtime, events included; (c) UI workflow test: the same steps through the React app with the fake API. (d) the real app (finding 7): a CI job `e2e` on Windows (WebView2, msedgedriver) and Linux (WebKitGTK, `WebKitWebDriver` under Xvfb) runs the built app through `tauri-driver` with a dependency-free W3C WebDriver script (`ui/e2e/workflow.mjs`): import the synthetic build, open the dashboard, edit an item and apply it, see the recalculation, undo, save, and export, with the file dialogs replaced by a test picker compiled only with the `e2e` feature of `loom-tauri`. Out-of-scope content (finding 6): the synthetic build's unsupported and indeterminate fields show their state and reasons, never a blank or a zero, checked in (a) and (c).

## Gate (objective, checkable)
1. `cargo test --workspace` on Windows and Linux (CI `rust`): the `loom-app` workflow test (including undo byte equality, reopen byte equality, reopen without data, recovery restore, and the out-of-scope states) and the `loom-tauri` IPC workflow test pass (decision 14 a, b).
1b. The CI `e2e` job passes on Windows and Linux (decision 14 d); if it cannot be made to run, the maintainer's smoke run on both systems is recorded in the report (commit, system, pass or fail per step) as a gate item.
2. `pnpm test` on Windows and Linux (CI `frontend`): the UI workflow test, axe checks on every screen, keyboard tests, and the contrast test pass (decisions 13, 14 c).
3. MCP contract tests pass: the tool list equals `schemas/mcp-tools.v1.json`; requests without the token, with a wrong token, or with a non-loopback `Origin` are refused; change requests are refused while the permission is off; a request waits for approval, applies on Approve as one undoable step, and is dropped on Decline; a standing grant applies at once and its revocation takes effect for the next request; a stale request is refused; a wrong `Host` header is refused; the 17th pending request is refused.
4. Schema freshness (CI `schema`) covers `app-api.v1`; `cargo clippy`, wasm (with `loom-pipeline`), deny, fmt green; `calc-run` on the public fixtures byte-identical before and after decision 0.
5. JavaScript dependency licenses checked by `pnpm licenses:check` (CI `frontend`) against an allow-list; `axe-core` (MPL-2.0, a test-only dependency, never shipped) is listed as an exception awaiting the maintainer's approval (finding 17).

## Fallback
If the Tauri mock-runtime IPC test cannot drive the commands, gate item 1 rests on the `loom-app` workflow test plus a test of each command handler called directly with a fake picker, and the report says so. If an axe rule cannot be met on a screen in this slice, the report lists it as an approved exception for the maintainer, never silently.

## Out of scope (named so the gap is visible)
Stages, dashboard customization, skills and skill group screens, passive tree, configuration editing, new build from scratch, character import from the game's website (a network adapter), PoE2 in-game build export, SQLite index, structured log files and diagnostic export (IMPLEMENTATION-PLAN Phase 5 WP7), installers, signing, and updates (Phase 5), the in-app assistant panel (deferred, ADR-017), MCP resources and prompts (tools only in contract v1).

## Risks and mitigations
- **The PR is large.** Mitigation: the steps above as separate commits; `code-architecture-reviewer` before the PR; every step has its own tests.
- **WebView differences.** The UI uses no API beyond what WebView2 and WebKitGTK 2.4x share; real-WebView smoke is manual now, automated in Phase 5.
- **MCP transport changes.** Contract v1 pins the protocol version; the transport is a small module with its own tests.
- **Reopen re-resolution changes results.** The byte-equality test (decision 7) catches it.
