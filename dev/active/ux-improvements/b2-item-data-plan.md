## Goal

The tooltip's Alt view shows what the game shows with Alt held (maintainer's screenshots, 2026-11-14):

```
Prefix Modifier "Urchin's" (Tier: 2) — Life, Defences, Armour
+34(33-48) to Armour
+28(24-28) to maximum Life
```

and the requirement line names attributes: `Requires Level 65, 85 Str, 62 Dex`. The game is the truth; PoB is the oracle (ADR-001/006). Everything here is **display only**: it never feeds line resolution or the calculation, so calc parity cannot move (ADR-015: a line with no identified mod keeps its text and gets no header).

## What exists

- Raw extraction already holds `Mods.Name` (the affix name), `Mods.Level`, `BaseItemTypes.DropLevel`, and `Tags.DisplayString` (the header's "Life", "Defences"); the bundle converter (`tools/parity-cli/src/bundle.rs`) drops them. Bundle mods carry `implicit_tags` (tag IDs), stats with ranges, `mod_type`, `generation`, spawn weights.
- `ComponentAttributeRequirements` (base → Str/Dex/Int) is not extracted: nothing references it.
- Many PoB items name their mods: `Prefix: {range:0.718}LocalBaseArmourAndEnergyShield4` (3607 prefix and 3591 suffix lines in the fixtures); `Prefix: None` for an open affix. Items imported from the game do not.
- `loom-parser::import::mods` has the row index, fit rules, spawn weights, essence and influence handling: the inference in PR 2 reuses them.
- This workstation has no game install: code and synthetic-table tests are done here; the maintainer re-runs `extract` and `bundle` on the main workstation.

## PR 1: data schema 4, exact headers, requirements

1. **Data schema 4** (converter and `loom-data`): `mods` gain `name` and `level`; `base_items` gain `drop_level` and `requirements {strength, dexterity, intelligence}` (from `ComponentAttributeRequirements`, a **PoE1-only** extraction root until PoE2's file is confirmed); a new `data/tags.json` lists each tag's `id` and `display`. Readers gate on `manifest.data_schema >= 4` (as `IMPLICIT_TAGS_SCHEMA`), not on empty fields; schema 3 bundles keep loading and show no names, levels, tags, or attribute requirements.
2. **Exact headers** (`loom-parser::import::affixes`, wasm-safe): an item's `Prefix:`/`Suffix:` spec lines naming a mod ID. The kind (prefix or suffix) is PoB's key, so no per-game generation numbers are needed. A spec is used only when the ID is in the bundle and the mod's stats account for the lines it is given: each explicit, non-crafted line whose resolved stats are all the mod's, with values in its ranges; lines may be anywhere in the item (a hybrid's lines are not always adjacent). A line two mods share (the game sums them: hybrid plus pure "increased Armour") goes under every mod whose stat it carries only when the sum fits their summed ranges; else it stays under no header. A stale or edited spec (unknown ID, stats that match no line) is dropped. `None` specs are open affixes and skipped.
3. **App API v1, additive**: `ItemCard.affixes: Vec<AffixView {kind, name, tier, tags, lines}>` in the game's order (prefixes, then suffixes), `lines` the line indices; `ItemCard.requirements: Option<{level, strength, dexterity, intelligence}>`, the level as written (`LevelReq`), else the base's drop level; attributes from the base (0 left out).
4. **UI**: the Alt view groups each mod's lines under its header (`Prefix Modifier "Name" — Tags`; no tier in PR 1), lines with no mod after them without a header; the requirement line with attributes.
5. **Evidence**: converter tests on synthetic tables; `loom-data` schema 3 and 4 load tests; `affixes` tests (exact, hybrid not adjacent, summed line, stale ID, `None`, unknown base tags); app workflow and UI tests; wasm32 build of `loom-parser`. The maintainer's run regenerates the bundle, the overlays and calc-run records (`data_schema` is part of their identity, `calc_run.rs`), and adds a `data-parity` table for mod `affix`/`level` and base `req` against PoB's `Data/ModItem.lua` and `Data/Bases` (`uncategorized` 0; differences registered).

## PR 2: inferred mods and tiers

- Lines with no PoB spec: candidates from the parser's mod filter (fit rules, spawn weights, essences, influences), one candidate or no header.
- Tier: the grouping key (mod type, family, or both) is proven against game-truth fixtures from the maintainer's screenshots (Urchin's, Tier 2 on a Pig-Faced Bascinet; Thorny, Athlete's, of the Lost, of the Genius, of Abjuration) before it is used; PoB has no tier oracle.
- Implicit (`Implicit Modifier — Tags`) and crafted (`Master Crafted Suffix Modifier "Name" (Rank: n)`) headers.

### PR 2, as built (2026-11-15)

- **Inference** (`loom_parser::import::affixes::item_affixes`): the lines no named mod took, in three pools (explicit, crafted, unflagged implicit). Candidate rows fit the line on the base and can be on it (explicit: spawn on the base's tags, an essence for its class or a legacy essence row of unknown classes, one of the item's influences, every row when the base's tags are unknown; crafted: any fitting row; implicit: the base's own implicit rows and rows that spawn), every row stat shown on a pool line. Lines no row spans are searched apart: every set of rows of distinct mod types whose summed ranges hold each line's value is an explanation, and a row is headed only when it is in every explanation (at most 8 rows and 20,000 steps per group, else no header). Unique items get no explicit inference.
- **Kind:** a new item rule, `ModRules.affix_generations` (prefix and suffix generation types, PoE1 and PoE2 both 1 and 2), written by `parity-cli`; rules without it infer no prefix or suffix. Not a data schema bump: rules, and no calculation reads it. The maintainer's bundle rebuild adds it.
- **Tier:** 1 plus the rows of the same mod type, domain, and generation with a higher level that spawn on the base's tags (no essence or influence rows); none for a row that does not spawn there, crafted rows, and implicits. Game truth: Urchin's Tier 2 on a Pig-Faced Bascinet (Nautilus's above; Crocodile's does not spawn on helmets). The helmet's five other mods give Athlete's 2, Thorny 2, of the Genius 2, of the Lost 6, of Abjuration 2, and all six match poedb's Str/Dex helmet tables (read 2026-11-15 through the maintainer's browser), which also number Urchin's armour and evasion rows apart, as the mod-type key does (`crates/loom-app/tests/game_truth_affixes.rs`, ignored, `LOOM_B2_BUNDLE`).
- **Strict on purpose:** on the helmet as the game exports it, Athlete's and of the Genius get no header: a legacy essence row of unknown classes (`IncreasedLifeEssenceChest1`) also makes the summed life line with Urchin's, and an essence row (`IntelligenceEssence7`) also holds 53 Intelligence.
- **Review (code-architecture-reviewer, 2026-11-15), taken:** a row's stat a line carries with no shown value (hidden, lookup) counts as on the item, so such a hybrid is a reading too; mod types the named mods hold are not inferred again; `named` reads selected lines only; a stat twice on one line no longer drops it; a unique's implicits only from its base's rows; no bases, no inference. Not checked, documented: the number of prefixes and suffixes (it can only take a header away). Measured: under 0.1 ms per item view in a release build on the real bundle, so nothing is cached.
- **Crafted rank** is left out: no game-truth fixture for its direction yet. Headers read `Master Crafted Suffix Modifier "Name"`.
- **App API v1, additive:** `AffixKind::Implicit`, `AffixView.crafted`, `AffixView.inferred`; `tier` filled.
- **Q-B2-2 (open, found by this PR):** the bundle's `data/tags.json` holds 20 monster tags only: `Tags.DisplayString` is empty for mod tags (`life`, `defences`), so headers show no tag names. Where the game keeps the names the Alt view prints is to be found on the main workstation. Leads (2026-11-15): RePoE's exporter reads `Tags.DisplayString` too, so no public export has them; poedb shows each mod's tag IDs in data order, title-cased, without `resource` and `physical_damage` (Urchin's "Life, Defences, Armour"; Athlete's "Life"; Thorny "Damage, Physical"; of the Genius "Attribute"; of the Lost "Chaos, Resistance"; of Abjuration none). **Research 2026-11-15 (the maintainer's browser):** the current game shows "Life, Defences, Armour" for Urchin's. Real Ctrl+Alt+C item copies on GitHub (the copy carries the Alt header lines): `Prefix Modifier "Nautilus's" (Tier: 1) — Life, Defences, Armour` and `"Fecund" (Tier: 2) — Life` (timeloop-vault/poe-inspect fixtures, March 2026), `"Urchin's" (Tier: 3) — Life, Defences, Armour` and `"Carapaced" (Tier: 6) — Defences, Armour` (poe-inspect), `"Beetle's" (Tier: 6) — Defences, Armour` and `Master Crafted Prefix Modifier "Upgraded" — Life, Defences, Armour` (PoB's `TestItemParse_spec.lua`), `"Fawn's" — Life, Defences, Evasion`, `"Prior's" — Life, Defences, Energy Shield`, `"Thorny" (Tier: 4) — Damage, Physical`. Copies from 2022 and before lack the Armour/Evasion/Energy Shield tag; the plan's earlier "— Life, Defences" quote was of that older form (it matches a hand-written comment in JIRPOS/PathOfPriceCheck), corrected above. So the game hides `resource` and `physical_damage`, as poedb does; what it does with the other compound or internal tags (`elemental_damage`, `caster_damage`, `chaos_damage`, `flat_life_regen`, `dot_multi`, `influence_mod`, `red_herring`, ...) is unknown. The only stated rule is 3.11.1b's patch note (tags shown were "just the tags used by Harvest and Fossil crafting", to be improved). The definitive check: copy current-game items with Ctrl+Alt+C, which also gives game-truth fixtures for every header (kind, name, tier, tags). **Shown now, partly unconfirmed (maintainer 2026-11-15: "show tags now"):** a per-game text rule `TextRules.mod_tag_names` names the tags the Alt view shows (tags not listed are hidden); PoE1's list is `MOD_TAG_NAMES` in `tools/parity-cli/src/poe1.rs` (27 plain gameplay words; the copies confirm Life, Defences, Armour, Evasion, Energy Shield, Damage, Physical; poedb shows Attribute, Chaos, Resistance; the rest by the same pattern). Compound and internal tags are left out. The maintainer's reminder task (Ctrl+Alt+C copies) is in `ux-improvements-notes.md`, "Maintainer tasks".
