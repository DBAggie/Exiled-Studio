# Passive tree editor and Phase 5 (plan)

## Summary
Two pieces of work in one PR, at the maintainer's request (2026-11-13: "complete the passive tree and phase 5 in the next PR"):

1. **The passive tree as a full editor** (maintainer 2026-11-13): allocate and deallocate with path finding, masteries, jewel sockets, ascendancy, cluster jewels, tree version switching. The action plan had the editor in Phase 6+ and ADR-008 orders "skills follow, then passive-tree editing". GGG's tree export becomes a data input, which ADR-005 does not allow today ("the project's own Rust extractor"; PoB "a cross-check only, not an input"). So step T0 carries **ADR-008 Amendment 1** (order, own shapes) and **ADR-005 Amendment 2** (GGG's published tree export as a pinned input for layout constants and older tree versions, with provenance), plus the action-plan change. Per `docs/adr/README.md` the maintainer accepts an amendment by merging the PR that adds it.
2. **Phase 5: packaging, signing, updates** (ACTION-PLAN Phase 5; IMPLEMENTATION-PLAN Phase 5 work packages 1 to 7): installers and portable packages, two-key signing (ADR-010 revised), prompted app updates, signed data bundles with rollback and quarantine, offline modes, security checks, performance baselines, structured logs and diagnostics (ADR-014; the Phase 4 report's limitation "structured logs and diagnostic export").

The plan, the implementation, and both reports go in one PR. `plan-reviewer` reviewed this plan on 2026-11-14 (4 blockers, 14 majors; context file, "Review"); this version takes in every finding. The PR is opened as a **draft right after T0**, so its number is in the handoff and CI runs on every push (review M14).

**Cut line (review M14; maintainer question MQ7).** Several weeks of work. If the budget runs out, the PR ships with: T0 to T2, T5a, T6, T7 on the bundle's own tree version, and P1 to P5; T3 (cluster jewels), T4 (older versions), T5b, P6 and P7 then follow in their own PRs. The order below puts the cut-line steps first.

## Current state (2026-11-14, `dev` at `218cdc0`, PR #106 merged)
- **Tree data.** Bundle format 2 carries the game's main passive graph (`data/passive_tree.json`: groups with centres, nodes with orbit and orbit index, connections, roots, `orbit_slots`), the passives table (stats as stat IDs, kinds), mastery groups and effects, classes, ascendancies. Not carried: orbit radii and angle tables, cluster-jewel tables (the extractor extracts `PassiveTreeExpansionSkills`, `...Jewels`, `...JewelSizes` as lookup tables for `resolve-corpus`), socket expansion data (`expansionJewel` size, index, proxy, parent), older tree versions. `Provenance` (`bundle/mod.rs`, `deny_unknown_fields`) records only the game install.
- **Calc.** `loom_calc::poe1::collect` applies the active spec's allocated nodes and mastery effects through the `CalcData` trait (`input.rs`; the P3-5 parity overlay is a second implementation), checks connectivity, gives `cluster-jewel-node` reasons, and requires the spec's tree version to equal the scope file's (`3_29`; `loom-app/src/data.rs` hard-codes `TREE_VERSIONS`). The P3-3 corpus survey had 37 `tree:version` and 27 `tree:unknown-passive` cases (mostly cluster nodes).
- **Domain.** `PassiveSpec` has nodes, mastery effects, sockets, tree version; class, ascendancy, and secondary (bloodline) ascendancy per spec are untyped attributes (build-level class and ascendancy are typed); PoB's `<URL>` child and `clusterHashFormatVersion` are untyped.
- **App.** Import, item edit, undo/redo, save, export, MCP; no tree commands, no tree screen, no tree mockup.
- **CI data.** Only synthetic bundles (`crates/loom-data/tests/fixtures/bundle-poe1`, a tree of about 4 nodes); real bundles are local (ADR-005). The oracle job fetches pinned PoB, whose `TreeData/<v>/tree.lua` holds GGG's export per version.
- **Release.** `bundle.active: false`, version `0.0.0`; no installers, updater, signing, logs beyond stderr, diagnostics. `cargo-deny` checks licenses, bans, sources; no advisories, fuzzing, or secret scan.

## Target state
**Tree.** A Tree screen draws the tree from the bundle in our own shapes; pan, zoom, search; hover shows a node's stats, the path that would be allocated, and the calculated effect (what-if); click allocates along a shortest path or deallocates a node and what it orphaned; pickers for mastery effects, socketed jewels, class, ascendancy; cluster jewels' generated nodes allocate; version switching shows what the conversion would drop before confirming. Each change is one undoable command, recalculated in the background, saved in build document v1, exported to PoB XML and share codes. A non-visual tree view does everything the canvas does (ADR-008). MCP clients read the tree and request allocations the user approves. Nodes loom cannot model are never removed by an edit (B3).

**Calc.** A spec on any tree version the bundle carries calculates with that version; modelled cluster jewels' generated nodes apply.

**Phase 5.** Signed Windows (NSIS, MSI, portable zip) and Linux (AppImage, .deb) artifacts from a protected release workflow; prompted, signed app updates where the artifact supports them; signed data bundles installed side by side, verified, pinned, rolled back, quarantined when unsigned; structured logs with redaction; a previewable diagnostic package; crash records; security and performance reports against budgets fixed in this plan.

## Design constraints and decisions
### Tree data and provenance
- **T-a. GGG's sprites, our shapes as fallback (maintainer MQ1, 2026-11-14: "Ship GGG's sprites").** GGG's developer data page lists the PoE1 tree export (`grindinggear/skilltree-export`, sprite sheets in `assets/`) as the one exception to providing game data; ADR-000 allows GGG assets "where GGG publishes them for tool developers". Neither the page nor the repository states a licence, and GGG's developer docs say "we cannot allow our Intellectual Property to be used to generate commercial revenue": the maintainer was told and accepted the risk (ADR-005 Amendment 2, Consequences). The sprite sheets are fetched with the export by `tools/tree/` at the pinned commit, copied unmodified into the data bundle (`trees/<version>/assets/`, listed and hashed in the manifest, signed), **never committed**; the CLAUDE.md and AGENTS.md hard rules name this one exception. The renderer draws sprites when the bundle has them and our own vector shapes otherwise (CI, synthetic and development bundles, or if GGG withdraws them); kinds (normal, notable, keystone, mastery, socket, cluster socket, class start, ascendancy start, ascendancy node) differ by shape and frame, never colour alone. The CSP gains nothing: sprites are served from the bundle through the app's own protocol, not fetched.
- **T-b. Positions from game data plus the export's constants (ADR-005 Amendment 2).** Position = group centre + orbit radius × (sin θ, −cos θ). The radii and slots per orbit come from the export's `constants` (`orbitRadii`, `skillsPerOrbit`); the 16- and 40-slot orbits' non-uniform angles from the export's own documentation (`skilltree-export` README at tag 3.17.0, which PoB's `CalcOrbitAngles` also cites), so PoB is not the input. They are carried in bundle format 2's new optional file `data/passive_tree_layout.json` with their source commit. The psg's group coordinates are used as stored, ascendancy groups included (PoB v2.67.2 applies no offset, `PassiveTree.lua` 873-876; the offset in `PassiveTreeView.lua` 606 is drawing only); layout parity (gate 1) checks this.
- **T-c. Provenance.** `Provenance` gains an optional `tree_export` block (repository, commit, the files read with SHA-256) and each tree pack carries its own provenance block; data schema 4 (review M9; see D-a). The bundle writer refuses an export checkout that does not match the pinned commit.
- **T-d. Tree versions.** A bundle carries the game's own tree (from the psg, stats as stat IDs) and older versions as **tree packs** `trees/<version>.json` converted from the export at commits pinned in `tools/tree/manifest.json`. `tools/tree/acquire.{ps1,sh}` (maintainer-run) fetches them into `local/tree-export/` with `git`; AGENTS.md's hard rule widens its `tools/oracle/` exception to `tools/tree/`, and `local/` is already ignored (MQ2). `loom-parity-cli tree-pack` converts one version: positions, connections, kinds, masteries, sockets, and node stat text resolved to stat IDs through `loom-parser` (ADR-015; an unresolved line stays as quarantined text and gives the calc a reason). Versions 3_25 to 3_29 first (the corpus's cases are 3_27 and 3_28); others as the corpus needs. Alternate and Ruthless trees are out.

### Tree model and rules
- **T-e. `loom-tree`, a new core crate; the calc stays independent of it (review M3).** `loom-tree` depends on `loom-domain` and `loom-data` (wasm32, `clippy.toml`, `CORE_CRATES`, the wasm build line in AGENTS.md and CI). Shared code: graph, kinds, positions, breadth-first search, conversion. PoE1 rules in `loom_tree::poe1` (masteries, radius jewels, cluster subgraphs, ascendancy rules), so PoE2 trees do not inherit them (ADR-001, review M2). It reads tree data through its own `TreeData` trait, implemented for the bundle and for the parity overlay, so PoB-valued runs still substitute. **`loom-pipeline` resolves the spec** before calculating: picks the spec's tree version, expands socketed cluster jewels into generated nodes with their stat IDs, computes connectivity; `CalcInput` gains a resolved passive set (nodes with stats, mastery effects, connected flags, reasons). `loom-calc` applies it and no longer reads `passive_links`. AGENTS.md: `loom-domain` <- `loom-data` <- `loom-tree` <- `loom-pipeline`. The Phase 3 calc documents stay byte-identical on the committed fixtures (checked before and after, CI `dto-compare`).
- **T-f. Allocation rules are PoB's where deterministic; ties are loom's (review B2).** PoB's breadth-first search seeds roots with Lua `pairs` order and neighbours from the export's `out` then `in` arrays (`PassiveSpec.lua` 1601, `PassiveTree.lua` 603-627), so which of two equal shortest paths it takes is hash order, not a rule. Loom's rule: the shortest path whose node list, ordered from the allocated set to the target, is lexicographically smallest by node number. Documented as a loom rule; `tree-parity` compares path **length and validity** always and **exact nodes only where the shortest path is unique**, counting tied cases as their own class (neither a match nor a divergence). The rest as PoB: class and ascendancy starts not targets; ascendancy nodes connect only within their ascendancy; a mastery takes one effect, an effect at most once per mastery group; deallocation removes the node and every node no longer connected to the start; Intuitive Leap, Thread of Hope, and Impossible Escape widen the allocatable set by their radius (radii from the game's jewel radius table, inclusion `distance ≤ radius` on `f32` positions widened to `f64`, the rule written and boundary cases listed by `tree-parity`); points counted as PoB's `CountAllocNodes`, shown, never enforced.
- **T-g. Nothing an edit cannot model is removed (review B3; ADR-014, ADR-015).** A spec can hold nodes the bundle lacks or does not model: bloodline (secondary ascendancy) passives (147 rows `not-carried` in P3-2), cluster nodes of unmodelled jewels, nodes reached through a timeless or unmodelled radius jewel. Every command except `ResetTree` and a confirmed `ConvertTreeVersion` keeps them in the spec untouched and counts them as connected for deallocation purposes (they are never orphaned by an edit); the tree view lists them as "kept, not modelled". `loom-tree` has a test per command. The secondary ascendancy is out of scope for editing and preserved, `secondaryAscendClassId` included on export.
- **T-h. Typed class and ascendancy per spec (review M5).** `PassiveSpec` gains `class`, `ascendancy`, `secondary_ascendancy` (typed from PoB's `classId`, `ascendClassId`, `secondaryAscendClassId`), and build document v1 gains them (additive). Export keeps the build-level and spec-level values consistent as PoB's `Load` expects (`PassiveSpec.lua` 128-179). An edited spec's `<URL>` child is regenerated in PoB's format (`EncodeURL`) or, if a case cannot be encoded, dropped with a note; an unedited spec keeps it byte for byte.
- **T-i. Cluster jewels (review M1).** PoE1 bundle section file `poe1/cluster_jewels.json` (not shared `data/`), from `PassiveTreeExpansionJewels`, `...JewelSizes`, `...Skills`, `...SpecialSkills` (notable sort order keyed by the stat row, cluster keystones) and `PassiveJewelSlots` (proxy node, size, start indices); the psg nodes gain their socket expansion data (size, index, proxy, parent; source checked against the psg and the export before T3 starts, recorded). A `data-parity` table against PoB's `Data/ClusterJewels.lua`. `loom_tree::poe1::cluster` builds the subgraph as PoB's `BuildSubgraph` (`PassiveSpec.lua` 1885): signal-bit IDs, orbit index translation, notable order, nested sockets. **Hash formats:** PoB's `clusterHashFormatVersion` 1 (legacy) and 2 (`PassiveSpec.lua` 95, 1651-1720); import reads the attribute and migrates legacy IDs atomically (ADR-009); export writes `clusterHashFormatVersion="2"`. The jewel's lines that drive the subgraph are stat IDs (ADR-015): passive count, small-passive kind, added notables, socket count, "Added Small Passive Skills also grant", "Added Small Passive Skills have X% increased Effect"; an unresolved driving line leaves that jewel's subgraph unbuilt with a reason. An ID that does not match PoB's on a corpus build is a reason, never applied to another node.
- **T-j. Timeless jewels' transformations are out**: the existing reason stays; the radius is marked "not modelled".

### Data versions (review M9)
- **D-a. What a build pins and what is compatible.** A build pins `DataVersion` (game, schema version, Steam build). This PR moves bundles to data schema 4 (layout, cluster tables, socket expansion fields, provenance). Migration: a build pinned to schema 3 of a Steam build calculates with a schema 4 bundle of the **same Steam build** (the game data is the same; the schema only adds fields); this is the compatibility rule, written in `docs/phase-5/data-bundles.md` with a test. A bundle of another Steam build is never used silently: the app names the pinned one and offers the installed ones, the user chooses (re-pin is one undoable command). App and bundle are compatible when the bundle's format is one the app reads and its schema is within the app's range (`loom_data::bundle::SCHEMA_RANGE`). The Phase 3 calc documents carry the data version: if the schema bump changes their bytes, the change is the version field alone, shown in the PR's `dto-compare` diff.

### API and UI
- **A-a. Commands.** T5a (bundle's own version): `AllocateNode { spec, node }` (path computed by `loom-tree`, never sent), `DeallocateNode`, `SetMasteryEffect`, `SocketJewel { spec, node, item: Option }` (non-cluster jewels), `SelectClass` (confirmed in the UI; resets allocation as PoB), `SelectAscendancy`, `ResetTree`, `NewSpec`, `RenameSpec`, `SelectSpec`, `DeleteSpec`. T5b: cluster jewels in `SocketJewel` and their generated nodes, `ConvertTreeVersion { spec, version }` with a `PreviewConversion` query. Every command through `Session::execute` (single writer, snapshot undo). Queries: `TreeLayout { version }` (static per version, cached by the UI), `TreeState { spec }`, `PreviewAllocation { spec, node }` (path plus slice-field delta, never committed). App API DTO v1 additive; schemas regenerated.
- **A-b. MCP (ADR-017).** Read: tree state, node details; write: `request_tree_change` (allocate, deallocate, mastery) through the approval flow; `schemas/mcp-tools.v1.json` diff reviewed.
- **A-c. Renderer (ADR-008 Amendment 1).** Canvas 2D for nodes, connections, orbits; DOM/SVG overlay for focus, hover card, search highlights; a spatial grid for hit testing; pan by drag and arrow keys, zoom by wheel, pinch, and `+`/`-`; reduced motion respected. No tree mockup exists: the design follows `docs/ui` tokens and is recorded in `docs/ui/fidelity/tree.md` for the maintainer's review.
- **A-d. Non-visual tree.** A searchable, filterable node list grouped by area and kind, with state (allocated, allocatable, path length, kept-not-modelled), keyboard allocate and deallocate, pickers, live-region announcements. ### Phase 5
- **P-a. Artifacts (review M6).** Tauri bundler: NSIS (per-user), MSI, portable zip; AppImage, .deb. WebView2: NSIS `offlineInstaller` mode, so installing needs no network ("fully useful offline", ADR-010); the MSI embeds the bootstrapper and says so. Versioning: SemVer from the workspace version, tags `v<version>`, the first release `0.1.0`; the version moves only in a release commit (review M7). A PR-time `package` job builds the portable zip and AppImage with throwaway keys and smoke-runs them (start, first screen, quit; AppImage via `--appimage-extract-and-run`, no FUSE on runners). The `release` workflow builds all five, then **installs, launches, and uninstalls** each silently (NSIS `/S`, `msiexec /qn`, `dpkg -i`/`dpkg -r`, AppImage extract-and-run, zip unpack), and asserts the `e2e` feature is off in release binaries (a symbol or build-info check). Gate 6 needs one recorded `workflow_dispatch` run of `release`.
- **P-b. Release workflow protection (review M8).** Secrets (`LOOM_UPDATER_KEY`, `LOOM_UPDATER_KEY_PASSWORD`, `LOOM_DATA_KEY`) live in a GitHub **Environment** `release` with the maintainer as required reviewer and deployment limited to `v*` tags and `main`; third-party actions pinned by SHA; the job drafts the GitHub release, the maintainer publishes.
- **P-c. Two keys (ADR-010 revised).** **App key**: Tauri's updater key (minisign Ed25519), one `pubkey` in `tauri.conf.json`; rotation = a release signed with the old key that ships the new public key (runbook). **Data key**: Ed25519 (`ed25519-dalek`, BSD-3-Clause) over the bundle manifest; public keys and key IDs in a trust list compiled into the app, with a revocation list of key IDs that ships with app updates. Verification is pure code in `loom-data` (wasm-safe, shared by every host; review M11). The maintainer generates the real keys offline (MQ6); tests generate throwaway keys. Runbook `docs/release/signing.md`. OS code signing is out (MQ4); SmartScreen and unsigned-package warnings documented.
- **P-d. App updates (review M7).** `tauri-plugin-updater` in `loom-tauri`, feed `latest.json` on the GitHub release. Self-updating artifacts: NSIS, MSI, AppImage. `.deb` and the portable zip only **notify** (link to the release), tested to never attempt an install. Modes: `automatic-check` (default), `manual`, `strict-offline`; every install is approved by the user; lower versions refused (downgrade test). TLS: the plugin's `native-tls` feature (rustls with `webpki-roots` brings CDLA-Permissive-2.0, not on the allow-list; review M12). Privacy (ADR-011): the check reveals IP address and app version to GitHub; written in the README's privacy notes and shown next to the setting. This is the one network path outside `loom-integrations` (a Tauri adapter, ADR-010); AGENTS.md says so.
- **P-e. Data bundles (reviews M10, M11).** A `.loombundle` is a zip of a format 2 bundle plus `signature.json` (key ID and Ed25519 signature over `manifest.json`; the manifest's reserved `signatures` field stays empty, documented). **Unpacking is hostile-input code:** signature verified on `manifest.json` read first from the archive, before anything is extracted; then entries must be exactly the manifest's files (count and sizes from the manifest, total uncompressed size capped at 1 GiB, no absolute or `..` paths via `plain_path`, no symlinks, no duplicates), each hash checked while extracting into a temporary folder, then an atomic rename into `bundles/<game>/<steam build>-s<schema>/`. On load the app verifies the signature over the manifest and the file sizes; full hashes are checked at install and on the user's "verify data" action (startup budget; tradeoff recorded). Several versions side by side; rollback = re-pin to an installed one; unsigned or unknown-key bundles are quarantined (stored, not loaded) until the user accepts them with their hashes shown. **Feed:** `data-feed.json` on the GitHub release, signed with the data key, carrying a monotonic sequence number; a lower sequence is refused (no feed rollback). Fetched by an adapter in `loom-integrations`, never in strict-offline. **Shipped bundle source:** the maintainer builds the bundle locally (ADR-005: CI cannot extract), uploads it as an asset of a draft release, and commits its manifest SHA-256 to `release/bundle.json`; the `release` workflow downloads it, checks the hash, validates it (`bundle-check`), signs it, and includes it in the installers. `LOOM_BUNDLE_DIR` and the folder picker stay for development, labelled unsigned.
- **P-f. Logs and diagnostics (ADR-014).** `tracing` with a JSON-lines file layer in `logs/`, rotation by size (5 MiB), 7 files kept; commands, calculations, imports, updates, persistence logged with the command's correlation ID; redaction by default (home path and user name replaced; build text, item text, and share codes never logged, only hashes and sizes). "Export diagnostics": a preview of each file and its redacted content, then a zip written only where the user picks. A panic hook writes a crash record; the next start offers the recovery snapshot and shows the record. Nothing is sent anywhere.
- **P-g. Security (review M12).** `cargo-deny` adds `advisories`; the ignores (expected: Tauri's GTK3 bindings, unmaintained) each with a reason in `deny.toml`; a secret scan job (gitleaks, pinned); `cargo-fuzz` targets under `fuzz/` (PoB XML reader, share code decoder, build document reader, signature verifier, `.loombundle` unpacker, feed reader) run by a scheduled workflow and the maintainer (10 minutes per target, recorded), plus `proptest` properties of the same entry points in CI; a Tauri capability check (the capability file equals a committed allow-list); signature, downgrade, rollback, quarantine, revocation, feed-rollback, zip-slip, zip-bomb, recovery tests. **Blocker** = an unignored RustSec vulnerability, a gitleaks finding, or an open fuzz crash. Report `docs/phase-5/security.md`.
- **P-h. Performance (review M13; ADR-013).** Budgets fixed now, on the reference tier (the maintainer's workstation, release build, the largest public fixture and the real 3_29 bundle): startup to first screen ≤ 2.0 s; import and first calculation ≤ 1.5 s; item-edit preview ≤ 300 ms; allocation preview (hover) ≤ 150 ms; tree first paint ≤ 500 ms and pan/zoom ≥ 50 fps; version conversion preview ≤ 300 ms; peak memory ≤ 600 MB; installer ≤ 40 MB without the bundle. `tools/bench` (`loom-bench`, core crates only) measures the core paths on the synthetic tree bundle in CI with an **instruction-count** measurement on Linux (stable across runners), failing on a 10% regression against the committed baseline; wall-clock budgets on the reference tier are maintainer-run and recorded in `docs/phase-5/performance.md`. Accessibility thresholds (WCAG 2.2 AA, axe clean, keyboard workflows) in the same report.
- **P-i. "Not affiliated" notice.** About dialog, installer licence page, README: "This product isn't affiliated with or endorsed by Grinding Gear Games in any way." (GGG developer docs.)

## Gate (objective, checkable)
**Tree** (written into ACTION-PLAN by T0):
1. Layout (MR, record re-validated in CI): every node of the bundle's tree within 0.01 units of the export's position for the same version, every node's edge set equal, class and ascendancy starts equal.
2. Allocation (MR): for the public fixtures and the seeded targets, path length and validity equal PoB's for every target; exact path nodes equal where the shortest path is unique (tied cases counted, not compared); deallocation sets, point counts, and version-conversion drops equal PoB's, or registered divergences with game evidence. `tree-parity` exit 0 or 19. ## Fallback
- A tree version with more than 1% of its node lines unresolved ships without that version; its builds stay `indeterminate` (`tree-version`).
- A cluster jewel kind whose subgraph does not match PoB keeps `cluster-jewel-node` and is listed; matching kinds work.
- Without the real keys in the release environment, `release` runs with throwaway keys; gate items 6 and 7 pass on those; a real release waits for the maintainer.
- Past the cut line: the PR ships the cut-line steps, the report lists the rest as the next PRs.
