- **C1: binary hashes are recorded per machine, not pinned in the manifest.** Measured: two Windows builds in the same folder are byte-identical (`/Brepro` through the `CL` and `LINK` variables), but `luajit.exe` and `lua51.dll` contain the build path (PDB path; `msvcbuild.bat` links with `/DEBUG`), so their hashes differ by folder, machine, and toolchain (CI included). So the manifest pins source commits, defines, and the expected `jit.version` and `jit.security` values; the acquire scripts write `local/oracle/build.json` (platform, commits, defines, compiler line, SHA-256 per built file); `oracle-verify` checks the files against `build.json` **and** runs the runtime (`luajit -e`) to check version, flags, and that `lua-utf8` loads and counts UTF-8. The probe is what ties the binary to the pin: `jit.version` embeds the commit time of the source it was built from. This replaces the plan's "per platform expected SHA-256 in the manifest".
- **C1: build flag `LUAJIT_SECURITY_PRNG=0`.** At `2460b3ff`, `src/lj_arch.h` defaults to `PRNG=1` (seed from OS entropy), `STRHASH=1`, `STRID=1`, `MCODE=1`; `lj_str.c` seeds string hashing from that PRNG (`g->str.seed = lj_prng_u64(...)`), so with the default `pairs` order over string keys changes per run. `PRNG=0` gives a fixed seed; the other three stay at their defaults. PoB's own runtime and test image use the default, so this is a harness choice, recorded in the manifest and checked by the probe (`jit.security("prng") == 0`). Not fixed by it: `pairs` order over table or function keys (hashed by address); C2a's repeated runs will show whether that matters.
- **C1: failure class for a bad manifest** is `ORACLE_ACQUISITION` (the pin itself cannot be read, so nothing can be shown acquired). Exit codes are fixed per class in `tools/parity-cli/src/oracle.rs` (10 to 20, taxonomy order); later PRs add variants, never renumber.

## Decisions in C2a (2026-11-10)
- **Startup errors:** `launch` is a global (`v2.67.2:src/Launch.lua` line 15, `launch = { }`), so the adapter reads `launch.promptMsg` after `dofile("HeadlessWrapper.lua")`; no upvalue tricks. The same field catches errors inside a build load (PoB's `launch:OnFrame` turns them into a prompt).
- **Stages and classes:** the adapter reports `startup` / `import` / `calculate` / `normalize` / `done`; `import` = the fixture is read, parsed with PoB's own `common.xml.ParseXML`, and has a `PathOfBuilding` root (the checks `buildMode:LoadDB` makes first). Anything later is `calculate`, so a well-formed XML that is not a usable build (no `Build` element) is `ORACLE_CALCULATION`, not `ORACLE_IMPORT` (reviewer N3; kept, to avoid copying more of `LoadDB`'s logic).
- **Adapter exit codes:** 0 done, 1 failure recorded, 2 no document; the CLI treats a mismatch between exit code and stage as `ORACLE_PROTOCOL`. No document with a non-zero exit is `ORACLE_LAUNCH`, with exit 0 `ORACLE_PROTOCOL`.
- **What is written:** `mainOutput` whole, plus 10 breakdowns from `calcsTab.calcsEnv.player.breakdown` (the Calcs tab's environment; `mainEnv` has no breakdowns). Selection measured over the 6 fixtures (182 breakdown names; most defensive ones in all 6; `Life` and `Mana` in 4, absent ones written as `null`): `Armour`, `ChaosResist`, `ColdResist`, `EnergyShield`, `Evasion`, `FireResist`, `Life`, `LightningResist`, `Mana`, `TotalDPS`, in the manifest (`adapter.breakdowns`).
- **Placeholders instead of game data:** `mainOutput.Req*Item` and breakdown slots hold PoB objects (an item instance pulled in about 400,000 nested values in OccVortex). Class instances (tables with a metatable) become `{"$object": "<class>"}`; gem instances are plain tables (one had a table-keyed map, `displayEffect.isSupporting`), so keys listed in `adapter.opaque_keys` (`sourceGem`) become `{"$opaque": key}`. Output is about 20 KB per build. Real string keys starting with `$` or `#`, table keys, non-UTF-8 strings, and nesting past 100 levels are `ORACLE_NORMALIZATION`.
- **Canonical form and hash:** Rust re-sorts every object explicitly (the workspace enables serde_json `preserve_order` through schemars) and writes pretty JSON; numbers come out in shortest round-trip form (`0.10000000000000001` -> `0.1`, `-0` -> `-0.0`). `output_sha256` is over the whole document, including `modules` and `settings.path`; C4's cross-platform comparison may need to exclude those two (reviewer note).
- **Windows paths must be ASCII.** Measured: LuaJIT opens files through the ANSI code page (code page 1252 here): a fixture and output under `Ä`/`ö` names ran `ok` with the same hash; under `日` the adapter could not open its output (exit 2). Whether a path works depends on the machine, so `oracle-run` refuses non-ASCII adapter, fixture, output, and runtime paths on Windows as `ORACLE_ENVIRONMENT` with a message, before launching.
- **Messages are scrubbed:** oracle dir, adapter, out dir, and fixture paths become `<oracle>`, `<adapter>`, `<out>`, `<fixture>`; `\` becomes `/`; `0x<hex>` becomes `0x?` (Lua addresses in tracebacks change per run). The launcher's own errors name only the program's file name.
- **Streams:** every run records stdout and stderr size and SHA-256; tails only for failed runs. Not part of the outcome (PoB prints `Startup time` etc.); whether stdout should count for determinism is open for C3.
- **Adapter record:** the report hashes every `*.lua` next to the adapter (`oracle.lua`, `json.lua`). `--adapter` can point elsewhere (needed for the fake adapters); the report shows which files ran (reviewer N8, not flagged further).
- `FailureClass` has variants 10-18 now; 19 and 20 (`ORACLE_EXPECTED_DIFFERENCE`, `ORACLE_UNEXPECTED_DIFFERENCE`) stay reserved until C3 adds them (an unused variant would need an `#[expect]`).

## Decisions in C2b (2026-11-10)
- **Adapter protocol 2.** The document gained `shims` (name, replaces, installed, detail) and `probe` (`inflate`: each call's input and output bytes, the stream's Adler-32, trailing bytes, error; `writes_refused`: paths in order).
